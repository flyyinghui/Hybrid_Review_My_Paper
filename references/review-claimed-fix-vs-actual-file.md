# 复审前必须独立验证前轮声称的修复（claimed-fix vs actual-file）

## 问题模式（2026-10-03 LightSpeed 复审暴露）

前轮终审报告的「修复状态表」声称「P0 修复 6/6 完成、已收敛到诚实自洽」，但论文文件实际**只改了头部注释/交付说明**（加了「已修复」声明），正文一字未动。

这是已知陷阱「P0 修复必须改正文/代码本身，仅加头注释 = P0 未修复」的**极端版**：不是头注释声称修复，而是**整份终审报告声称修复、论文文件完全没改**。

## 检测（复审前必做，不能信任前轮报告）

复审前先 grep 论文文件，独立验证前轮声称的每项修复是否真正落地：

| 检查项 | grep 示例 |
|---|---|
| 标题是否真改 | `grep -n "^# " 文件`（对比前轮要求的诚实措辞） |
| 计数是否真统一 | `grep -c "22 theorems"`（旧值残留数） |
| 作者名/首字母 | `grep -n "G. Coleman"`（应为 S. Coleman） |
| 状态升级措辞残留 | `grep -n "deepening open bridge\|advance\|necessarily\|main theorem"` |
| 编号对齐 | `grep -n "^| 1[5-9] \|" 文件`（Sec V.B 表顺序 vs Lean 声明顺序） |

**核心判据**：前轮报告的「修复状态表」可能是在「假想修复」基础上写的（审稿建议了如何修，报告记录了「应已修」，但从未实际执行文件修改）。因此复审的已知缺陷 verdict 必须基于**当前文件的实际 grep 结果**，而不是前轮报告的自述。

## 案例：LightSpeed_Phase_Boundary.md

前轮 `5Agent终审报告_20261002.md` 声称「6/6 P0 修复完成」，但论文文件实际残留：
- 3 处 `"22 theorems"`（P0-5 计数，应 29）
- `G. Coleman`（P2-2，应 S. Coleman）
- 标题仍是 `"A Formal Proof that...Equals"`（P0-6 过度声称）
- `### D. Real-section existence (deepening open bridge 1)`（P0-3 状态升级）
- Sec V.B 表 #16 排在 #15 前面（P2-1 编号错乱）

第二轮复审 5 个审稿人一致判 P0-5 / P0-6 / P2-1 / P2-2 全部 **REMAIN**（完全没修）。

## 修复闭环（用户期望的标准流程）

1. 复审抓出残留 → **真正执行文件修复**（不是只在报告里声称）
2. 修复用 Python 批量精确替换：`old→new` 对，带唯一上下文（如 Lean 定理名）避免冲突，逐项打印命中次数 + 未命中清单
3. 改完 grep 验证残留清零（标题/计数/作者名/措辞/编号）
4. 复跑复审验证 fixed/remain/partial
5. 机械修复清零后，剩余诚实性表述层问题 → 按 `review-convergence-stopping-rule` 判断是否收尾（P0/P1 连续两轮清零 + 核心卖点未被击穿 = 收尾，否则陷入 P2/P3 无限递归）
