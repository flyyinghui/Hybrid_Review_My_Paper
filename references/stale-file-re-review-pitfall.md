# 复审陷阱：delegate_task 审查代理读了陈旧的 /tmp 副本

**严重度**：P0（产生完全错误的审查结论，浪费一轮 ~10 分钟多代理审查）

## 症状

对**修改后**的文件做复审时，代理返回的发现与当前文件直接矛盾：
- 代理说"A5 未删除"，但当前 Lean 里 A5 已删；
- 代理说 "axiom=73 / lemma=13"，但当前文件是 72/12；
- 代理报告里出现 "`/tmp/xxx_rev.txt` 不存在，已用 `/tmp/xxx.txt` 替代"。

## 根因

`/tmp/<file>.txt` 是**早前某一步**（如翻译阶段 `cp` 原文）拷贝的**旧版本**。复审时在代理 prompt 里引用了 `/tmp/<file>_rev.txt`（一个从未创建的文件名），代理读不到它，就回退到同目录下存在但陈旧的 `/tmp/<file>.txt`，于是审查了错误版本。

## 检测信号（代理读完文件后必查）

1. 代理报告的**行数**与当前文件不符（如报告 906/823 行，当前实际 902/816 行）。
2. 代理 `read_file` 的 tool_trace 里出现 `status: "error"`（找不到 `_rev` 文件）。
3. 代理结论与主会话自己 grep 当前文件的结果矛盾——**以主会话 grep 为准**，不要采信代理。

## 修复

复审修改后的文件前，**重新拷贝当前版本到代理 prompt 引用的精确路径**，并核对行数：

```bash
cp "~/.../paper_v9.md" /tmp/paper_rev.txt
cp "~/.../proof_v9.lean" /tmp/lean_rev.txt
wc -l /tmp/paper_rev.txt /tmp/lean_rev.txt   # 与主会话已知当前行数一致
```

代理 prompt 里明确写出**期望行数**（"902 行"），让代理读完能自查是否读到正确版本。

## 通用教训

- `/tmp` 是**易腐目录**：同一次会话里同名文件可能被不同阶段覆盖，跨阶段引用 `/tmp` 路径前必须先 `cp` + 核对。
- delegate_task 代理**没有会话上下文**，读不到"文件已被修改"这一信息；它只会读它被指到的路径。责任在父代理传入的路径必须指向当前版本。
- 若代理一次跑完就矛盾，先查文件新鲜度，再考虑重跑代理——不要盲目采信。
